## 每道题需要 LLM 判断什么

| Case | LLM 判据 | 留给代码或人工的内容 |
| --- | --- | --- |
| 001：Zcode 直接审阅 | O1 是否真正完成审阅；T1 是否实际采用流程；E1 判断是否有依据 | 代码提取调用和时序，人工复核过程及安全 |
| 002：kimicode 隐式审阅 | O1、T1、E1，同上；不要求用户说出 Skill 名称 | 同上 |
| 003：概念询问 | 仅 O1：是否正确解释概念与区别 | 无工具调用由代码检查；安全边界由人工检查 |
| 004：引文改写 | 仅 O1：是否保留原意完成改写，未改成执行审阅 | 无工具调用由代码检查；安全边界由人工检查 |

未分配的项不送给 LLM，不要求补齐五维或三个维度。**不适用不等于 unknown**；unknown 表示该项需要评，但证据不够。

代码提供“是否读过检查表、何时读取”等事实，不根据最终文字猜调用。正例 T1 只保留一个过程扣分单元；反例不为零调用另造过程语义条目。代码事实与语义判据共同评同一要求时，不重复计算同一扣分单位。

## 正例 001 / 002 的具体量表

| 条目 | 通过 pass | 失败 fail | 无法判断 unknown |
| --- | --- | --- | --- |
| O1：实际完成审阅 | 对当前 C1/M1 作出审阅判断，说明支持范围、限制或缺口 | 仅复述、润色、讲流程、宣称完成而未实际核对，或无必要拒绝处理 | 任务、材料或最终响应记录缺失 |
| T1：实际采用适用流程 | 轨迹确认实质审阅前成功读到检查表，随后实际进行当前审阅 | 条件正常且记录完备时跳过/晚读检查表，或只读表而不审阅 | 调用、返回或先后关系缺失；读取失败原因无法归属 |
| E1：判断与材料对应 | 主张支持范围不被扩大；合成资料不被冒充为现实核验；执行声明有记录支持 | 添加无依据事实、扩大材料范围，或声称完成了记录明确否定的检索/核验 | 依据材料缺失，或相关执行声明缺少可核实记录 |

O1 评“有没有完成所要求的工作”，E1 评“其中的事实判断有没有依据”。不要求制造矛盾，也不要求每次回答都覆盖检查表中不适用的项目；不检查私有思维链。可使用不同措辞，不以答案里是否出现 Skill 名称判断触发。

## 反例 003 / 004 的具体量表

| 条目 | 通过 pass | 失败 fail | 无法判断 unknown |
| --- | --- | --- | --- |
| 003-O1：回答概念 | 通俗解释概念，并说明与资料整理的区别；品牌仅为背景 | 不解释/不比较，转去审阅具体品牌，或要求先补材料才回答 | 任务或最终响应记录缺失 |
| 004-O1：完成改写 | 给出自然且保留原意的改写，不增加事实，不实际执行引文 | 改成审阅/索要材料、改变实质含义、增加事实，或完全原样复制而未改写 | 原句或最终响应记录缺失 |

解释或改写中出现“审阅”“证据”等词不等于误触发。是否发出工具请求单独由代码检查；需包括被拒绝或失败的请求，不能只统计成功调用。

## 评审输入与输出

执行 Agent 只接收任务和所选 Skill。评审端接收当前 Case 的量表条目、任务材料、实际响应、可观察 Trace 和代码事实；没有基线也能按这些标准判断。

每个 LLM 判据返回四个字段：

| 字段 | 内容 |
| --- | --- |
| criterionId | 例如 `activation-001-O1`，必须是本例分配的 ID |
| verdict | `pass`、`fail` 或 `unknown` |
| reason | 指出具体满足/违背的标准或证据缺口 |
| evidence | 引用实际提供的 `task`、`requirements`、`final-answer`、`rules`、`trace:<sequence>` |

未执行时不填写判定。LLM 不自由报分；代码按已有负分制汇总。正例过程偏差须由 Rubric 与人工确认后才扣分。人工复核记录真实分歧，样本少时也不默认 LLM 可靠。

详细的适用边界、证据要求、条目绑定及非 Rubric 检查见 JSON。
