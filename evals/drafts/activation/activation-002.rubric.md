# Case 2：判定条件与扣分对照

本页把 Case 2 现有 JSON 判据与全局负分制对应起来，供人工一起查看。具体判据见 [结构化 Rubric](activation-002.rubric.json)，全局计分见 [统一负分制](../../../docs/penalty-scoring.md)，程序实现在 [penalty.ts](../../../scripts/evaluation/penalty.ts)。本页不修改既有 Case、量表内容或已确认基线，也不表示项目所有者已批准这份量表。

起始 100 分，最低 0 分。LLM 返回 pass/fail/unknown、理由和证据引用，分值由程序计算。

| 条目 | 何时判失败 | 扣多少 | 判定来源与去重 |
| --- | --- | --- | --- |

## 待审与未计分情况

- 任务、材料、回答或必要轨迹缺失，不能判断相应语义项时记 unknown；不能仅凭资料不足把它当成已证实的内容错误。
- 完整人工模式中，T1 的 LLM 与人工分歧、任一方未知或缺少人工意见时，该过程项待审，完整总分为 null。自动模式不冒充人工共同确认。
- 若已确认 O1、E1 或安全硬失败，可先记 0，但其他未判项仍保持未完成，不能宣称评审完整。
- 单一材料、未联网、未生成文件、没有制造矛盾、回答措辞不同、未主动补充用户没有主张的套餐或导出格式，本身不额外扣分。
- Token、费用和调用数记录实际值，本例未另设按这些指标扣分的项目；未知费用不能填 0。

## 计算示例

| 情况 | 单次得分 |
| --- | ---: |
| 所需判定全部通过，主任务不超过 5 分钟 | 100 |
| 最终核对正确且证据成立，但完整记录证明未先读取检查表，T1 已确认失败 | 90 |
| T1 已确认失败，且主任务耗时 5 分 30 秒 | 80 |
| 只读检查表，没有实际核对当前材料，O1 已确认失败 | 0 |
| 实际进行了核对，但作出 E1 明确不受材料支持的判断 | 0 |
| 缺少必需判定，尚无已确认否决 | null / 待审 |

普通单次数值门槛为至少 80 分，并仍需满足必过项。正式五次自动回归另有更严格门禁：每次自动项必须 100 分，所有必需代码检查及 Rubric 条目均 pass，且已有兼容的 confirmed 基线；不能把 90 分视为正式回归通过。

## 已确认基线与本量表的关系

用户确认的是 runId=667dbd08-2375-41e2-ba55-64aa00173fd1 的真实 Trace 和 Outcome；那次纯执行试跑没有调用 Judge，也没有自动评分。其回答中关于“一手材料”和功能开始日期的措辞原样保留，并在确认前披露。这份基线不自动批准旧 Rubric，也不能据此宣称该回答在现有 E1 下必然 pass。正式测试前须把这两处与 E1 的判定边界对齐；不能静默放宽规则，或按结果临时改分。
