## Case 1 的触发定义

本项目的用户扩展 Skill 由工作台或 CLI 显式选中。这里测的是**已加载 Skill 后，Agent 能否依据本轮意图判断适用并采用流程**，不是自然语言自动安装、搜索、选择或切换 Skill。产品依据见[通用 Agent](../../../docs/generic-agent.md)和[用户扩展](../../../docs/user-extensions.md)。

Case 1 与 Case 2 的材料块逐字相同，Skill、工具面、预算、权限和模型配置保持一致，各自在全新会话运行。只改变任务意图：核对与排版。两题 Prompt 均不告诉 Agent Skill 名称、资源路径、调用顺序或标准结论。

观察基于宿主实际记录：Skill 是否加载、资源工具是否披露、模型实际请求了什么、返回是否成功、调用与最终响应的先后关系。单看回答写“已审阅”不能证明采用了 Skill；单看读取了一份资源也不能证明任务完成。缺少 Trace 或资源不可用属于试跑条件问题，须如实保留。无需私有思维链。

Case 1 只用一条短主张和一段角色限定材料；日期推断、来源比较、多来源冲突和报告质量由其他 case 承担。最终如何把触发、过程与业务结果映射为扣分项，待纯执行基线审核后独立冻结，避免把同一次错误临时拆成多项扣分。

## 执行条件与输入

- Case 1/2 的输入文件分别为 [case-01.input.json](case-01.input.json)、[case-02.input.json](case-02.input.json)。它们符合现有 `InputSchema`，不是带 `expected_*` 的完整 `CaseSchema`，不能传给 `eval:run --dataset` 冒充已注册题单。
- 两份输入冻结同一份 `competitor-review` 入口及检查表，来源为原 `activation-001 r4` 已归档的 Skill 内容。仅复用公开能力与配置，不包含历史答案、量表、评分或基线确认。
- 通用真实 Agent，`pi_session`，`source=none`，外部来源为空，`explore`，总 Token 预算 30000，输出上限 8192，工具调用上限 8。由模型自行决策，不提供脚本步骤或预制调用。
- Case 3–10 使用同一审阅 Skill，业务材料均在 Prompt 内，默认不联网。Case 11/12 需要另行冻结可控只读工具返回，工具名与失败条件见各题；本轮尚未配置这些工具。
- Case 13/14 直接给定已核对事实，只测交付；不加载审阅专家 Skill，不额外考业务推理。不要求业务文件落盘，交付为最终响应。
- 全部品牌能力、产品名、文档标题、日期和内容均为合成测试数据。没有访问现实品牌网站，不将其视作真实产品事实。

## 评分与 Langfuse

场景回答“测什么”，五维回答“从哪些角度评”。沿用 100 分起始扣分制、现有 P0 否决、过程计分单元去重与耗时规则；未知或未完成评审不能作为满分。每题仅分配适用评审。

代码适合验证真实调用、错误、权限、结构、JSON、耗时和 Token；语义需要时才交给 LLM 或人工。Langfuse 记录实验、Trace、逐项判定及原扣分程序产生的扣分明细与总分，不把评委的 `pass/fail` 直接当作全项目 0/100 计分。具体评分契约和评委启用规则尚未创建。
